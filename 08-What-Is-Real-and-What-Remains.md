# What Is Real and What Remains

![Ideas, tests, failures, and verified capabilities crossing distinct implementation gates](assets/evidence-implementation-gates.png)

## Evidence classes

The evidence model keeps several classes distinct:

- **primary evidence:** preserved source artifacts and interaction events;
- **derived evidence:** extracted text, semantic units, relationships, classifications,
  temporal observations, and other versioned representations;
- **execution evidence:** manifests, call observations, costs, model identities, and
  stage results;
- **acceptance evidence:** independent invariants, receipts, promoted bundles, and
  exact output hashes;
- **design intent:** architecture and planned behavior not yet proven in execution;
- **historical claims:** what a prior release or experiment reported about itself.

A passing test is evidence only for the envelope it exercises. A release document is
not proof that the current runtime still matches it. An installed library is not a
deployed capability.

## Implemented foundations

The implementation has demonstrated the following bounded foundations:

- content-addressed source preservation and append-oriented evidence handling;
- separate artifacts, representations, locators, and source events;
- actor- and sequence-bound conversation events;
- discourse and coreference preprocessing with bounded source slices;
- argument relation classification with exact source spans and retained attempts;
- a typed proposition-and-relation graph;
- deterministic dependency projection;
- request-scoped Personal Meaning Matrix contributions with uncertainty and
  protection flags;
- backward selection and same-graph forward replay objects in bounded tests;
- globally owned semantic-unit allocation and interlaced artifact planning;
- grounded rendering floors and optional candidate comparison;
- independent receipt-gated promotion;
- durable artifact jobs and a reasoning viewer;
- a public-document publication boundary with content-addressed releases.

These statements describe demonstrated component boundaries, not a claim that the
entire vision is complete.

The demonstrated comparison also records an external-cog boundary. A frontier model
received a prepared, request-specific payload and contributed a more polished
rendering without receiving the maintained corpus or becoming release authority. The
evidence supports that bounded transaction; it does not establish what any provider
retains outside the tested artifact path, which remains a separate contractual and
privacy question. It does establish that the useful contribution did not require
transferring the human record for destructive reduction into provider-owned value.

## Installed platform scale

A bounded filesystem inventory of the installed application tree counted about
566,000 files and 218 GiB. Model assets accounted for roughly 172 GiB, dependencies
and language runtimes for 25 GiB, data state and other assets for 20 GiB, and
implementation source for about 184 MiB. The inventory encountered some unreadable
or changing entries, so these are operational scale estimates rather than a software
bill of materials.

The asymmetry is intentional evidence about the architecture. Source code is a small
part of the installed footprint; model weights and reusable runtimes dominate it.
The control plane therefore tracks the value, authority, and operating cost of each
specialist rather than treating installed size as capability. A future distributable
code release needs an artifact-specific dependency inventory, exact versions,
licenses, hashes, and reproducible build boundary.

## Engineering lessons preserved by the design

Development produced several durable engineering lessons:

- prompting a general model to simulate a missing specialist;
- treating a process exit or self-reported manifest as proof of capability;
- running discourse after semantic classification and duplicating specialist work;
- assigning the first repeated quote occurrence as provenance;
- allowing one whole-file evidence item to make composition unverifiable;
- treating zero accepted relations as pipeline failure;
- confusing a deterministic graph projection with a separately executed specialist;
- matching a weave profile while producing unsupported or unreadable prose;
- debugging with whole-corpus runs when small and medium cases exposed the defect;
- tuning one product in a way that could regress another.

The public architecture retains these corrections because they explain the purpose
of the current constraints and make future refinement more reliable.

## Current development opportunities

Several major capabilities remain incomplete or require broader evidence:

- relation labels need independent expert-quality evaluation, not only structural
  validation;
- cross-deposit temporal links and reattribution need continued testing at larger
  mixed-source boundaries;
- high-level personal drivers must remain unpopulated until source-bound evidence and
  lens behavior justify them;
- different product types need calibrated, regression-protected assembly lines;
- Human Protocol feedback needs longitudinal outcome evidence;
- figurative and narrative mechanisms require product-aware evaluation before
  authority is granted;
- full public documentation requires continued editorial review as the private record
  evolves.

## Validation ladder

Development proceeds from small to large:

1. pure schema and invariant fixtures;
2. short semantic examples with known topology;
3. small real source slices;
4. medium mixed-format and mixed-time slices;
5. larger scalability boundaries after earlier levels pass;
6. human-authored versus system-generated comparison under the same evidence,
   receiver, form, and budget.

The comparison diagnoses whether loss came from graph selection, importance
allocation, forward replay, realization, or final readability rather than assigning
every defect to generic “model quality.”
